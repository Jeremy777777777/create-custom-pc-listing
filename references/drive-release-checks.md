# Product release checks — 2026-10-26

[Drive delivery](google-drive-delivery.md) owns storage layout and authorization. These checks make its boundaries reproducible. They use supplied connector observations; none authenticates a remote account, uploads files, grants style/QA approval or locks Drive. Continue the existing run record instead of creating a second product status system.

## Before replacing current files

Resolve the exact product/current IDs and load the last verified Drive receipt and original ledger, style lock and affected dependencies. Record their actual hashes. Existing Git history checks cover retained Git fixtures only; a new Drive product needs this Drive baseline. A missing baseline is HISTORY_CONTINUITY_UNVERIFIED, not an inferred clean history. Preserve current bytes in the established archive and reconcile the baseline before overwriting them. First delivery requires a completed accessible destination search proving no previous product delivery; a failed search is not first delivery.

Use one writer per product in the current coordinated work. Immediately before writes, read back the targeted current file IDs, parents and checksums again. `delivery_context.py revision --baseline <baseline.json> --observed <fresh.json>` compares exact inventories. Both inputs contain `productId`, actual UTC `readBackAtUtc` and `files` rows with `relativePath`, `id`, `sha256`, `parentFolderId`. Include the current delivery marker in this comparison. A changed/moved/missing file or new competing revision stops overwrite for reconciliation. This check is not a remote transaction/lock: use provider conditional writes when actually supported; otherwise serialize writers and verify immediately after writes. Never claim race-free execution from offline comparison alone.

For ledger changes, run `delivery_context.py history --previous <downloaded-previous-ledger> --current <new-ledger> --previous-sha256 <observed-baseline-hash>`. Obtain this hash from the verified previous receipt or the completed legacy baseline adoption below. It rejects a scoped-ledger downgrade or product/configuration substitution. Keep complete old coherent bundles, conflicts, approvals and source evidence archived; the helper does not prove archive preservation or authenticate the baseline. A legitimate configuration change needs a separately identified/reconciled configuration, not relabelling the previous one. Unrelated product history is outside this check.

Prepare all files and archive old coherent bytes before replacing current files. Reuse stable IDs. If a write is uncertain, read back before retrying. If any dependent file fails, mark DELIVERY_INCOMPLETE and record changed/unchanged IDs and repair actions; do not update the completion marker or delete the only local copy. Publish the run's completion marker/current summary last, after all listed bytes and roles pass. Consumers use that manifest to detect a mixed/incomplete current view; stable file IDs do not provide atomic multi-file replacement.

### Existing product without a qualifying old receipt

Adopt an observed baseline for the requested revision; do not classify an existing delivery as first delivery or require a nonexistent historical receipt. Within the already-authorized same-product scope:

1. Complete accessible paginated discovery and read back the exact product folder chain, existing current file IDs, parents and metadata. Download the affected workbook/ledger, current marker if present, style approval and all dependencies needed to preserve the previous coherent bundle. Compare downloaded bytes with provider checksums or a second authenticated readback. Record each file's actual SHA256, size, parent and observation time; explicitly record missing prior artifacts/marker.
2. Inspect identity/configuration and source applicability. Preserve the observed old bundle in the established product-history archive, retaining original relative paths, old review states and source links. Verify archive IDs, parents and byte hashes against the observed originals. Do not recreate missing historical evidence, invent old approvals or recertify old images. If old records contain excluded private content, retain the original in its existing authorized location and record a sanitized derivative with its transformation; do not expand delivery authorization to archive those private bytes. A missing dependency blocks only work that needs it.
3. Save a baseline-adoption section in the existing run record with `state: LEGACY_BASELINE_OBSERVED`, product/configuration, discovery and identity review, the current inventory, archive readback inventory, missing artifacts and `historicalQa: UNASSESSED` (or the accurately preserved prior state). This records observations made now, not historical delivery success. Save and verify that record through the existing run/archive path. Its verified old-ledger hash may now supply `history --previous-sha256` and the research reuse review's `baselineReference`.
4. Immediately before replacement run the ordinary fresh revision comparison; a change requires reconciliation. Proceed with the requested scope once identity, observed bytes and preservation are established. If no prior ledger exists, record that absence after completed discovery and construct current evidence for affected facts; the legacy research-reuse option cannot be used without actual prior ledger bytes. If old files disagree, preserve the observed set as incoherent and resolve affected dependencies before replacement, rather than labelling the set coherent.

Missing old receipts alone no longer block a revision. Inaccessible files, ambiguous identity, unverified preservation or unresolved dependencies retain their specific blocker and follow-up action. Adoption never grants style, factual or publication approval.

## Privacy of actual deliverables

Run `delivery_privacy.py check-file --input <file> --serials-used yes|no [--private-values-file <private-list.json>] [--visual-review <inspection.json>]` on each planned file. If raw serials/service tags were used in the run, the actual known-value list is mandatory, stays private and is deleted only after verified delivery. Do not declare no merely to bypass this requirement.

The helper screens JSON/text and every XLSX XML/relationship part, including hidden cells, comments, hyperlinks and document properties. Images have metadata screening plus actual visual privacy inspection; XLSX embedded media/objects and unsupported formats also require inspection. The separate inspection contains the exact `sha256`, `result: NO_PRIVATE_CONTENT`, actual `reviewer`, `reviewedAtUtc` and substantive `notes`. It must describe actual inspection, never a generated PASS. Unknown sensitive content still needs review. A no-pattern result cannot establish licensing, hardware fidelity or complete privacy clearance. Keep original evidence private and create a sanitized derivative when needed; never alter facts to satisfy screening.

Known numeric serials are checked in JSON numeric values as well as strings, including exact decimal/exponent representations and nested values. JSON decimals are parsed without binary floating-point rounding. Findings contain only locations and reason codes, never matched serial values. This does not recover identifiers already truncated or rounded by an earlier system; retain the actual private known-value inventory and inspect ambiguous source transformations.

A normal HTTP(S) website path such as Dell's `/support/home/en-us/` is not a local Unix home directory. This syntax distinction does not exempt known private values, credentials, signed/serial URLs, Windows/file/UNC paths, standalone Unix paths or paths embedded in query strings/fragments. It does not certify a page's access, factual support or public sharing.

## Product directory and receipt

For new production deliveries, the supported CLI also requires `--production-contract` and `--contract-sha256` under [production guardrails](production-guardrails.md). It checks actual file changes, product/configuration, style bytes, run ID and roles, then runs workbook/image gates before storage verification. Retain the digest independently before edits. Storage-only API receipts do not substitute for production checks.

The `drive_delivery.py verify` CLI now requires `--context <context.json>` in addition to plan/readbacks/destinations. The context contains:

- `productId`, `serialsUsed` boolean and `folders`: current connector folder observations with `id`, `name`, `mimeType`, `parents`, `readBackAtUtc` and optional `trashed`. Read them after plan creation. Include pinned project/products roots, one exact internal-ID folder and the relevant section/FINAL children.
- `fileRoles`: each exact planned relative path maps to RESEARCH, LISTING, IMAGE, QA or SOURCE. Research uses `03_RESEARCH/FINAL`, listing `01_LISTING`, canonical images `02_IMAGES`, reviews `04_QA`, supporting production assets `90_SOURCE`. Workbook stage/role is grounded in the existing workbook checks, never guessed from a filename alone. Canonical role checks apply to top-level current files. Nested same-name masters/records must be explicitly SOURCE, not current image/workbook slots.
- `privacyChecks`: each planned path maps to its actual-byte `check-file` result. All hashes and serial-use declarations must match. Shareable readbacks remain separately projected with `share-readbacks`.

The verifier checks the pinned project/products chain, exact product and role folders, current privacy screens, and original byte/metadata comparison. Missing context on the lower-level Python API produces only DRIVE_BYTES_MATCHED_CONTEXT_UNCHECKED, never DRIVE_DELIVERY_VERIFIED. Connector authenticity, actual previous-version preservation, completed prewrite/history checks and real review remain required operating evidence in the run record.

For SOURCE, preserve every directory segment of the product-relative path below `90_SOURCE`: `unbranded/PT01.png` goes to `90_SOURCE/unbranded/PT01.png`, and `production/run-a/layers/mask.png` goes to `90_SOURCE/production/run-a/layers/mask.png`. Include a fresh folder observation for each segment; duplicate names, missing parents, wrong-product folders, shortcuts and flattened destinations cannot pass. A root `PT01.png` remains a canonical IMAGE and cannot be relabelled SOURCE. Original relative paths inside recipes remain intact. Remote archive/run records outside the product sections use the established archive/run procedure and their own verified readbacks; do not pretend they are SOURCE files under the product root merely to pass this verifier.

## One completion report

Use separate existing run-record fields for: research outcome/unresolved counts; Research Review and Listing Draft stage; USER style approval and preview/recipe reference; current scoped image QA; exact delivered-file inventory/receipt; workflow SHA and backup scope; publication NOT_EXECUTED or actual separately authorized state. A directory called FINAL, eleven filenames, candidate-filled cells, a test pass or a GitHub push cannot substitute for these states. Keep screenshots/previews outside the eleven canonical current slots.

Evidence reuse is bounded by current identity, configuration, bytes, parents and applicable policy. Changes invalidate only dependent facts/outputs/reviews; they do not revoke an unchanged user-approved style direction or force unrelated product research.

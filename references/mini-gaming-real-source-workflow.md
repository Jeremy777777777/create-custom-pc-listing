## 2. Build a source library that can be reused

Search existing registered originals first. For missing media, inspect the relevant official game/publisher media page, press kit, authorized supplied library or applicable product photo source, and acquire its actual image file. Record both the observed source page and original asset provenance; do not invent direct links or call a search thumbnail a reviewed original. Distinguish inaccessible, not researched and not found. Confirm MIME, decoded format, native dimensions, transparency, byte size and SHA256. An HTML error page with a `.jpg` name is not an asset.

For every used source record:

| Field | Required meaning |
| --- | --- |
| `assetId`, `kind`, `gameId` or `hardwareIdentity` | Stable exact identity; `GAME_ART`, `GAME_LOGO`, `PRODUCT_PHOTO`, `BRAND_MARK` or qualified `TECHNICAL_ILLUSTRATION` |
| `sourcePage`, `sourceOriginal`, `acquiredAtUtc` | Actual inspected provenance; original source may be supplied-file/Drive reference when applicable; no credentials or signed transient links in shared records |
| `sha256`, `mimeType`, `nativeWidth`, `nativeHeight` | Actual original bytes, not just output filename |
| `rightsBasis`, `authorizationScope`, `authorizationSource` | Existing applicable seller assertion/permission; no claim that download availability grants commercial rights |
| `driveFileId`, `parentId`, `recipePath` | Verified storage linkage and portable relative recipe path; not an unresolvable local cache |
| `derivatives` | Parent SHA, crop/mask/resize/compositing method and output SHA; preserve the original |

Use [registered original hardware/software marks](reusable-brand-assets.md) for applicable CPU/GPU/OS identities. Match the real tier and edition; an Office mark does not prove paid Office inclusion. Keep original logo geometry, colors and aspect ratio, and protect its artwork while removing only eligible background. Never trace a logo, retype a stylized mark or use an AI substitute. Use a genuinely supplied alternate original colorway when needed. No arbitrary recoloring to fit the red theme.

Games require both an accurate identity and readable naming. Use the original game logo embedded in the artwork when readable, or place the corresponding original standalone logo as a separate layer. Add the correct English game name in a consistent caption as well; do not confuse sequel/version identities. A plain title caption identifies the picture but does not replace a requested original logo. If an original cannot be sourced, record the limitation and use another covered source/game or a visibly incomplete proposal; do not manufacture a logo.

Keep full-res originals, masks, recipes and final product files in the established authorized Drive source/product structure. GitHub holds reusable rules, source metadata, templates and scripts; do not commit product output galleries, raw serials or downloaded game binaries merely because their use in MegaPC ads was authorized. Do not create duplicate asset libraries or change access settings.

## 3. Plan information before drawing

Create a per-product `information-plan.json` from [the planning template](../assets/mini-gaming-information-plan-template.json). Each page must answer one buyer question with a clear primary theme, a short headline, meaningful visual proof, grouped supporting details, canonical fact IDs and applicable original asset IDs. Usually one main visual and two or three related supporting groups work well; these are layout guidance, not a rigid fact count or a quota to fill. Technical/port pages may need more labels. ### Nonrepetition with useful secondary context

Assign every canonical fact a primary explanatory page. Normalize aliases, units and scope before comparing claims; two IDs or paraphrases for the same fact do not create new information. Only PT03 provides the complete sold configuration. Do not repeat the same CPU/RAM/SSD list, generic slogan or six-icon strip across every page.

A fact may appear as `SECONDARY` on another page if a recorded `reuseReason` explains its distinct buyer purpose and the page adds new visual/detail evidence. For example PT03 identifies installed memory/storage; PT05 can explain their roles without presenting the entire configuration again. Count repetition by meaning, not text alone. Do not reject justified explanatory reuse solely because an arbitrary overlap percentage was exceeded. Record actual manual semantic review; an invented numeric overlap score or a passing structure check cannot establish useful information design.

## 4. Strong gaming language with defensible facts

Classify each game panel's purpose:

- `GENRE_CONTEXT`: an editorial original-art portfolio, not proof of playability, included software, free downloads, endorsement or a test. Use a concise contextual qualification such as “Game images illustrate gaming genres; games sold separately” where needed to prevent ambiguity. Do not pair it with “plays smoothly”, “supports all these games” or implied FPS promises.
- `VERIFIED_PLAYABILITY`: requires current-configuration applicable compatibility/test evidence with its limits; minimum hardware requirements alone do not prove smooth play. State relevant settings/conditions and avoid universal guarantees.
- `BENCHMARK`: requires actual current sellable-unit test evidence, game/version, resolution, quality preset, API, driver, RAM configuration, power/mode, test method/date and units. Display only the matching measured result with legible conditions. Do not copy another seller's FPS, add a decorative `±`, extrapolate from a related processor or depict a comparison as measured without test evidence.

Gaming strength should come from real CPU/GPU identity, installed memory/storage, actual controls, supported expansion and connections. Write concise specific English; no unsupported “ultimate”, “dominate”, AAA/4K/high-FPS/silent claims. Decorative chip art, fan arrows or a game logo never establishes a factual performance result. Keep supported capability visibly distinct from installed/supplied configuration. Warranty stays in authorized copy, not an image filler page.

## 5. Layered production recipe

1. Save original source bytes unchanged. Build clean product cutouts from supported angles; preserve proportions, marks, openings and shadow. Record masks and protected regions. Do not cover mismatched branding with a new logo or fabricate unseen detail.
2. Compose background, original game panels and technical modules independently. Set real crops for every game; reserve protected logo/name areas before placing the foreground product. The product may overlap scenery, never the only game identity, a factual label or an important control/port.
3. Add genuine matching original logos as locked-aspect layers, then deterministic English captions, verified specifications, labels and leaders. Keep fact/asset IDs attached to individual copy/layer entries. Do not bake old wrong copy into a flattened master and merely add correct copy on top.
4. Record actual canvas dimensions, color profile, source/derivative hashes, relative layer paths/z-order, crop and scale, opacity, masks/protected regions, logo bounds, fonts/license/size/line breaks, leader endpoints and deterministic render command. Rebuild from a self-contained pack with no dependence on temporary absolute paths, browser caches, signed URLs or another product's coordinates.
5. Export opaque high-quality sRGB finals under the current [image size policy](image-spec.md); no fixed 2000-square mandate or forced upscaling. Product contact sheets and technical masters are supporting records, not extra final slots.

## 6. Inspect actual output and correct it

At 200px product silhouette and main message must read; at 400px game names/logos and grouped technical copy should be clear. Do not claim every small port label is readable at 200px when it is not. Full-resolution detail remains required.

Review actual hardware geometry/material/branding against sources; verify every game picture/title/logo match and protected area; compare every factual sentence to its applicable ledger evidence; check inch axes, installed versus maximum capacities, modes, counts and protocols. Inspect crop seams, old text remnants, duplicated labels, halos/jaggies, letterbox bars and dark edges lost into the background. Recompose or source a better image; do not enlarge a deficient source to pass pixel limits.

Review the entire retained gallery for primary-page ownership and useful secondary reuse. Save substantive actual findings against current final hashes and input bindings; update current selected-slot logo, visual and semantic reports using [per-image dependencies](image-review-dependencies.md). Never fill PASS records without inspection. Use [the gallery engine](amazon-product-image-workflow.md) for supported prepare/accept operations and existing production/delivery gates. A targeted correction accepts exactly its selected files and binds retained inventory; it does not promote a quarantined legacy gallery into a full-gallery PASS.

Distinguish automated structure, factual review, visual review, authorization basis and Amazon publication review. Python passing is not aesthetic judgment, measured playability or Amazon eligibility. A workflow-only update does not constitute new image QA or product approval.

# Physical dimensions in inches — user decision 2026-10-27

User reaffirmed on 2026-10-30: all newly produced or revised physical size outputs use inches. Convert the value from its actual source unit before writing; never relabel centimetres or millimetres as Inches. Source/evidence quotations retain their original units for verification.

Current image review uses the explicit numeric pairs below in both directions: naming a size also binds its unit, and revising a unit also checks its associated value. The value and unit must have applicable verified/not-applicable status, and a depicted numeric size requires the literal Inches unit. Unit source/status changes invalidate the dependent review. The dimensions policy/source binding applies only to pages that depend on dimensions; historical policy retains its original hash shape.

All actual customer-copy entry points also check physical measurements, including bare metric/feet captions and screen-size labels. Standard audio-connector names such as 3.5mm audio jack remain technical designations, while an explicitly labelled body measurement still requires inches. Actual pixel inspection remains necessary.

For imageFactUpdate, check only the declared fields and their explicit dimension value/unit pairs. New or changed dimensions in that scope must satisfy the inch rule. Unchanged dimensions elsewhere remain unassessed and cannot block a port-only update or receive a new approval. Full/new workbook generation and full export continue checking all applicable dimensions.

All new physical length/width/height/depth/thickness measurements use inches in Research Review, Listing Draft, candidate rows, customer copy and image dimension labels. This includes chassis dimensions, package dimensions, screen diagonal and bezel thickness. Paired workbook unit fields contain **Inches**; self-contained dimension strings say **inches**. Preserve canonical field names/Definitions and axis order. This overrides older examples/defaults using mm/cm/feet for physical dimensions.

Retain original source values, units, URL, excerpt, configuration/scope and date in evidence. Convert before finalizing the scoped ledger and its reference-audit hashes. Unit conversion does not establish a new measurement, sold-unit applicability, package size or confirmation status. Keep unresolved values blank and candidates unconfirmed. Source quotations/evidence keep their units. Component/interface names such as M.2 2280 and 3.5mm audio remain recognizable technical designations; image pixel dimensions, resolution, weight, electrical and storage/frequency units retain their own meanings.

Use the exact constants in [dimension-units-policy.json](../assets/dimension-units-policy.json): mm ÷ 25.4, cm ÷ 2.54, m ÷ 0.0254, feet × 12. `scripts/dimension_units.py` supplies `to_inches(value, source_unit)` for scalar values and `convert_length_text(text)` for explicit shared-unit ranges/tuples. Keep full calculation precision until one final rounding to four decimals; strip insignificant zeros in text. Never round a positive measurement to zero. Do not infer a missing source unit or collapse a thickness range into one number.

Examples: 254 mm → 10 Inches; 25.4 cm → 10 Inches; `17.9–18.9 mm` → `0.7047–0.7441 inches`. A range that cannot fit a scalar template Definition remains a qualified candidate/text record, with the scalar formal value unresolved. Evidence must distinguish item dimensions from packaging; no packaging estimate from chassis measurements.

Preserve maximum/minimum/nominal qualifiers and explicit position labels, rather than flattening them to one measured thickness to satisfy a text format. The converter retains a trailing `maximum`, `minimum` or `nominal` and supported contexts such as `(OLED chassis)`, `(with stand)` and `(without stand)`. For a tapered/profiled chassis, use an explicit footprint followed by individually unitized positions, for example `10 x 5 inches; front 0.5 inches, rear 1 inches, maximum 1.5 inches thickness`. The footprint axis order and each position remain as sourced; front/rear positions are not sorted as if they were uncertainty bounds. Each input clause needs an explicit source unit. The parser rejects missing/mixed output units, duplicate/unknown position labels, reversed named ranges and contradictory minimum/maximum bounds. It never invents a missing position or classifies a nominal maximum as an actual measurement.

`validate_dimension_text(text)` validates these bounded inch representations in confirmed and candidate dimension-text fields; `convert_length_text(text)` converts the explicit source units first, while preserving those labels and qualifiers. The original source text and scope still remain in evidence. An unsupported source layout requires an explicit evidence-preserving representation review, not deletion of its qualifiers or an arbitrary-prose escape in the validator. Existing product contracts stay immutable; a workflow-version change requires a separately linked pre-edit stage before further product writes.

Explicit three-axis tuples may retain one order label such as `(W x D x H)`, `(W x H x D)` or `(L × W × H)`. The converter preserves the original coordinate order and label, including a range on an individual coordinate: `254 x 127 x 12.7–25.4 mm (W x D x H)` becomes `10 x 5 x 0.5–1 inches (W x D x H)`. Labels use three distinct axes from L/W/H or W/D/H, with T permitted instead of H for explicit thickness; other combinations require representation review. Exactly three scalar or bounded-range coordinates must match the three labels. Duplicate labels, a second order label, reversed coordinate bounds, unknown axes and arbitrary parenthetical prose are rejected. A maximum/minimum/nominal qualifier precedes the optional order/context labels; supported chassis/stand context may appear immediately before or after the order label. An axis label does not establish a physical measurement, a package size, current configuration or scalar-field orientation; preserve the source and confirmation status separately.
